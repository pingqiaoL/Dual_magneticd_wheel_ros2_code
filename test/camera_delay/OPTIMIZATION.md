# 视频延迟优化与验收

2026-10-20，已应用到 Nano 正式工作区并安装 Android 0.8.10（versionCode 25）。原启动命令继续适用。

## 最终结果

正式版本自然播放 75 秒，前 15 秒排除：**待播缓存中位数 156 ms、P95 173 ms、最大 186 ms，渲染 29.85 FPS**。解码器渲染丢弃增量 0，没有 STALL_TIMEOUT、PLAYER_ERROR、BACKLOG 或 CODEC_ERROR。

有 4 次短 BUFFERING，累计 74 ms、单次最长 25 ms，其中稳定区间 2 次。此前同条件长轮为 2 次、累计 56 ms；本轮缓存降低的同时仍存在短缓冲，不能声明完全消除了卡顿。单轮时间有限，尚未完成运动、无线干扰和长时间验收。

相较此前两组中位数 175 / 184 ms，最终减少约 **19–28 ms（约 11%–15%）**。这是播放器待播时长的改善，未重新测量实景到屏幕延迟，也未实现先前预估的 70–80 ms 改善。

## 最终配置

| 项目 | 优化前 | 已采用 |
|---|---|---|
| Android 追帧目标 | 180 ms | 100 ms |
| Android 触发门限 | 300 ms | 180 ms |
| 连续超限时间 | 300 ms | 200 ms |
| 追帧速度 | 1.1 / 1.2 倍 | 保持原有速度范围 |
| Nano appsrc / 原始帧 queue | 各 2 帧 | 各 1 帧，过载丢旧 |
| Nano 最大帧年龄参数 | 500 ms | 150 ms |
| 视频格式 | 720p30、6 Mbps、veryfast、zerolatency、B 帧 0、GOP30 | 保持 |

150 ms 分别用于 ROS 入口消息年龄和工作线程内部等待检查，不能当作曝光到编码、或曝光到屏幕的总耗时上限。只在原始图像侧丢旧帧，不任意删除已压缩的 H.264 参考帧。

单帧队列主要限制过载时可能保留的旧图像。候选组和最终组没有证明它单独进一步降低了稳定播放缓存，不将安卓与 Nano 的收益混为一谈。

## Android 对照

各候选采集 90 秒，通常排除前 15 秒。80/150 轮起始阶段与 Nano 测试副本编译有重叠，排除前 30 秒；它不作为严格等负载的最佳延迟比较，但其频繁短缓冲仍记录并排除采用。

| 目标 / 触发 / 持续 ms | 稳态缓存中位数 / P95 ms | 全窗口短缓冲次数 / 总时长 | 结论 |
|---|---|---|---|
| 100 / 180 / 200 | 152 / 168 | 3 / 53 ms | 采用，进一步进行最终安装后验收 |
| 80 / 150 / 200 | 134 / 158 | 46 / 869 ms | 短缓冲明显增加，未采用 |
| 100 / 150 / 200 | 136 / 162 | 36 / 516 ms | 触发过于频繁，未采用 |
| 120 / 180 / 200 | 157 / 177 | 4 / 70 ms | 未显示额外收益，未采用 |

这里的次数来自真实状态回调，部分事件仅 5–35 ms。它们不能直接等同于用户每次都可感知的卡顿，但不能因为平均 FPS 仍接近 30 就忽略。没有把最小缓存、最激进配置当作最终结果，也未声称差异经过统计显著性检验。

候选数据目录依次为 `results/android_20261020_205623`、`205858`、`210117`、`210420`；正式最终验收为 `results/android_20261020_211129`。`summary.json` 保留完整目录与窗口信息。

## Nano 与停顿恢复

测试副本通过组合加载、第二图像消费者、H.264 RTSP 解码、双客户端、停止后继续采集、端口冲突恢复、重启、输入超时、停止重发旧帧、非法/过期图像拒绝、退出释放端口检查。

真实发送候选进程先暂停 250 ms，再暂停 800 ms；每次均在 finally 中恢复进程。800 ms 停顿触发预期的播放器 STALL_TIMEOUT 和自动重连。恢复后缓存回到约 150 ms，没有在本轮形成持续约 1 秒的待播积压。这是模拟发送侧停顿，不是无线干扰测试。

该轮包含主动注入故障，出现的 17 次 BUFFERING、一次较长等待和 STALL_TIMEOUT 不能用于宣称自然播放零故障，也不与自然播放轮直接比较。数据：`results/nano_candidate_20261020_210731`、`results/android_20261020_210739`。原始暂停时刻用 Nano 单调时钟记录，没有拿两台设备绝对时钟直接相减。

正式 Nano 最终资源轮 `results/nano_20261020_211132`：CPU 全核能力占用中位数 43.72%、P95 69.83%；eth0 总发送中位数 6.28 Mbps，收发错误和丢弃计数增量 0。视频快照之间收到/提交 2570 帧、编码 2568 帧、丢弃增量 0；快照窗口包含辅助命令，不据此计算精确 FPS。没有观察到 CPU 开销明显改善，也不把网卡零错误解释成无线零丢包。

## 复查与回滚

当前无需额外传参数。按原方式运行 `activate/robot.sh` 或摄像头单模块入口即可使用新队列和 150 ms 门限。

Nano 容器内复核：

```bash
python3 /workspace/test/camera_delay/verify_optimized_runtime.py
```

原 APK 在 Ubuntu 虚拟机 `test/camera_delay/results/optimization_backup/original_0.8.9.apk`，原 Nano 三份源码在机载端同目录的 `nano_sources/`。回退涉及降级已安装版本和重新编译，应根据当前工作区状态进行，不直接重跑一次性 promote 脚本。脚本保留并发修改校验，防止覆盖后续开发。

更低缓存策略已被实测否决；若继续追求明显低于当前水平，应先测完整光学延迟及解码/显示等待，避免反复降低缓冲引入短暂停顿。
