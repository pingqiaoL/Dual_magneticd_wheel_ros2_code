# 视频延迟整体排查结果

> 本文记录优化前的排查状态。当前已部署版本与实测结果见 [OPTIMIZATION.md](OPTIMIZATION.md)。

日期：2026-10-20。设备：Orin Nano、真实 USB 摄像头、天空端、MK32。正式安卓版本 0.8.9 / versionCode 24。

## 结论

**当前最明确、优先级最高的优化位置是安卓待播缓存：稳定播放约 175–184 ms。** 本轮没有观察到持续增长到半秒的积压；正式播放器约 29.7–29.9 FPS，统计稳定区间内解码器渲染丢弃增量为 0。不能因此断言所有场景都不会卡顿。

Nano 此前同日测得 V4L2 元素输出到 H.264 输出中位数约 45 ms；图传完整帧接收并经 UART 返回确认的闭环约 45 ms。这些结果不支持“编码器或网络平时固定积压半秒”的判断，但没有单独覆盖曝光、摄像头内部缓存和实际屏幕呈现。

本轮**没有重新测得完整玻璃到玻璃延迟，也没有测出精确单向无线延迟**。不能将表中不同轮次、不同边界的中位数相加，给出一个伪精确的端到端总数。用户此前照片中的约 140 ms 本地显示、约 370 ms 遥控显示，仅是单张照片估计，不能替代本轮同步光学验收。

## 链路与证据

```text
曝光/摄像头缓存/USB → V4L2 输出 → 解码为 BGR → ROS/编码队列 → H.264/RTP
      尚未独立计时          └──── 同日分段测试约 45 ms ────┘       │
                                                              ↓
                                          以太网/无线 → 安卓收帧
                                                │       ↓
                                  ACK 闭环约45ms │    待播缓存约180ms
                                                │       ↓
                                                └─ 数传  硬解码/计划释放/屏幕
                                                          尚未完整分离
```

图中的 ACK 闭环包括视频到达、准备 ACK、数传返回和 Nano 解析，不等于纯无线单向耗时。待播缓存也可能覆盖接收、解码队列中的部分时间，不能机械相加。

| 环节 | 实测/核查结果 | 判断边界 |
|---|---|---|
| 摄像头实际输出 | MJPEG 1280×720、30 FPS；状态 CAPTURING，重连计数 0 | 曝光与摄像头内部缓存未分离；设备未暴露曝光控制项，未改相机参数 |
| Nano 内部分段 | 同日原始 CV 路径 V4L2→GUI 调用返回 28.57 ms；V4L2→H.264 44.75 ms，整机组 45.03 ms | 不是曝光到屏幕时间；本轮复用原始计时结果并重新核验正式源码 SHA256 一致 |
| 物理网络路径 | eth0 上被动捕获到 Nano `.144.129` → MK32 `.144.20` 的高端口 UDP；同时仅一个 RTSP 客户端 | 当前没有回退到 RTP/TCP；包头检查不测丢包率和单向时延 |
| 图传接收闭环 | 同日 60 帧：中位数 45.33 ms，P95 57.96 ms，最大 114.86 ms | 包含数传回程；无解码/渲染负载的独立接收器，与正式播放器负载不同 |
| Android 待播缓存 | 两个长轮稳定区间中位数 175 / 184 ms | 当前最明显的可优化等待，不是完整播放器或端到端延迟 |
| Android 计划释放提前量 | 两长轮中位数 46.29 / 44.24 ms | 不是解码耗时；可能与待播时长有重叠，不能额外直接相加 |
| 屏幕实际呈现 | 本轮未作光学测量 | Surface 回调/计数不等于像素已经出现在面板上 |

## 本轮正式 App 实测

长轮采样 75 秒，排除采样前 15 秒。日志只取采样后新增行，防止历史文件中重启后重复的 uptime 污染统计。短轮用于补充首帧样本。

| Android 目录后缀 | 条件 | 稳态缓存中位数 / P95 / 最大 ms | 渲染 FPS | 首帧等待 ms |
|---|---|---|---:|---:|
| `201550` | 已在播放，75 秒 | 175 / 192 / 197 | 29.88 | 本轮无重连 |
| `201716` | 重开 App，75 秒 | 184 / 225 / 237 | 29.74 | 640 |
| `201934` | 重开 App，20 秒 | 短观察，不作长期结论 | 约 29.80 | 624 |
| `202006` | 重开 App，20 秒 | 短观察，不作长期结论 | 约 29.89 | 649 |

三次首帧等待包括 RTSP 建链、启动缓存、关键帧条件及解码器初始化，不能全归为 GOP。解码器初始化分别为 51、53、54 ms；首帧时缓存分别为 332、300、299 ms。首帧之后恢复到较小的稳定缓存，所以约 0.64 秒启动等待不等于一直落后 0.64 秒。

`201716` 轮稳定播放期间有两次短暂 BUFFERING，之后 READY，未出现 STALL_TIMEOUT、PLAYER_ERROR、BACKLOG 或 CODEC_ERROR。其余三轮也没有这些异常事件。稳定渲染计数差分中 dropped 增量为 0，但这不能排除网络损坏帧在进入解码器之前被丢弃。没有针对高速运动与干扰进行长时间压力验收。

两个长轮缓存前/后三分之一中位数为 169→174 ms、181→187 ms，当前窗口未见数百毫秒持续增长。播放器仍保留约 180 ms 的等待，并不等于零积压。

## Nano 负载与发送状态

`nano_20261020_201658`：75 个资源样本。CPU 按全部核心能力归一化，中位数 43.25%，P95 67.39%，最大 89.00%；可用内存最低约 3.92 GiB。CPU 峰值存在，不能仅由平均值排除瞬时调度延迟或单核瓶颈。

eth0 总发送速率中位数 6.29 Mbps，P95 6.49 Mbps；收发错误、丢弃计数增量均为 0。该值包含该网卡所有流量，不是独立编码净码率，也不代表无线链路完全不丢包。

状态快照之间收到 2,570 帧、提交 2,551 帧、编码 2,536 帧，丢弃计数增加 19。快照范围包括辅助命令与 App 重开过程，不直接把这些计数除以 75 秒作为精确编码帧率。累计 dropped 超过四万主要来自之前长时间无客户端等历史状态，不能拿累计值判定本轮大量丢帧。单轮增加 19 帧也不能全部归因于 CPU。

## 当前配置中值得优化的点

| 优先级 | 当前状态 | 建议与风险 |
|---|---|---|
| 1 | Android 源码追帧目标 180 ms；超过 300 ms 且持续 300 ms 才触发，1.1/1.2 倍追帧 | 独立测试版先试目标 80–100 ms、触发 150–200 ms，与现版本交替测。减少缓冲可能增加短暂停顿，需同步比较卡顿和损坏帧 |
| 2 | Nano appsrc 和 queue 各允许 2 帧，下游丢旧；max_frame_age_ms=500 | 测试副本可试各 1 帧、旧帧门限 100–150 ms，重点看 CPU 峰值时尾延迟。现有测量没有证明它们稳定占满，不能承诺必然减少数帧延迟 |
| 3 | x264 veryfast、zerolatency、B 帧 0、6000 kbit/s、GOP 30 | 暂不盲目提高码率或更换编码器。GOP 可在启动对照中试 10–15；关键帧更频繁可能增加码率峰值、降低同码率画质 |
| 4 | 仍缺少传感器→面板的同步测量 | 用真实计时器与 MK32 同镜头高帧率录像，至少 20 个样本；Nano 直连显示器一起入镜，避开 NoMachine 的额外显示链路 |

当前 Android 源码的策略与实测缓存同量级，但未通过修改后 A/B 证明优化幅度；本轮没有改变这套策略。

GStreamer 插件显示 `vbv-buf-capacity` 默认 600 ms，**不能据此断言编码器固定增加 600 ms**。它是码率缓冲参数；同日实测 V4L2→H.264 约 45 ms 已反对“此处固定等待 600 ms”的解释。`zerolatency` 也不能只看插件未实例化的默认 lookahead 属性来判断是否生效。

此前同日首轮 ACK 有约 1,026 ms 异常样本，仍保留，当前无法区分出现在图传还是数传回程。本轮不能用平均结果抹去该异常；需要更长时间接收与渲染关联采样定位长尾。
