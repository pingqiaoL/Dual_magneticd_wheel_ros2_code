# 数传 RTT 与视频帧确认测试

## 先测数传往返时间

在容器内执行：

```bash
source /opt/robot-venv/bin/activate
python3 /workspace/test/camera_delay_test/telemetry_rtt.py --count 60
```

脚本识别并暂时停止现行组合入口，独占 `/dev/ttyTHS0`，采用 115200、8N1。先发送心跳，再每秒发送一次带序号和唯一时间标记的 MAVLink PING；收到目标为 1/191、来源为 255/190 且原样返回序号与标记的响应才匹配。两秒未返回记为超时。结束或异常后重新启动原组合入口，原查看器保留运行。

计时从 Nano 请求构造/写入前开始，到完整响应解析完成结束，统一使用 Nano 单调时钟。它包含双向串口线路、无线传输和安卓响应处理，属于应用 RTT，不是精确单向无线时延。当前测试暂停了视频和测厚；后续使用帧 ACK 校正时，应在视频实际负载和相同接收处理路径下复测。

结果在 `results/telemetry_时间戳/`，包含 `samples.csv`、`summary.json` 和恢复日志。脚本只发送心跳及 PING，不发送机构动作命令。只有已知组合入口恰好运行一份时才自动管理进程。

### 报文兼容性

首轮标准 pymavlink PING 会使用 MAVLink 2 的尾部零截断，广播目标 0/0 位于负载尾部。已知安卓代码直接要求 payload.length >= 14，未补齐截断的零，因此可能忽略这类合法报文。

当前测试器改为发送完整 14 B 负载的合法 MAVLink 2 PING，并重新计算 CRC。安卓后续应将合法 MAVLink 2 负载补零后解码；不应依靠发送端总是不截断。当前运行 APK 的源码版本仍需核对，不能仅凭旧源码认定其具体实现。

## 视频帧确认（已完成独立测试）

已通过 test 目录下的独立 Android 接收器与 Nano 仪表化副本完成真实链路测试，没有接入或修改正式 APK。完整协议、运行方法和误差边界统一见 [VIDEO_LINK_TEST.md](VIDEO_LINK_TEST.md)，结果见 [VIDEO_LINK_REPORT.md](VIDEO_LINK_REPORT.md)。

同轮有效采样为 60 个视频 ACK 和 60 个 PING。RTP 末包输出到 ACK 返回的闭环中位数 45.33 ms、P95 57.96 ms；同轮数传 RTT 中位数 83.40 ms。使用邻近 RTT/2 扣减后有 18 个负估计，因此不报告可靠的单向图传数字。不能使用此前视频暂停时的 RTT 基线代替当前回程耗时，也不能把完整帧接收当作屏幕显示。
