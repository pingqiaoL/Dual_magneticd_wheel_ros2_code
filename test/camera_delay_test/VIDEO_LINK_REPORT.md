# 图传接收与数传确认实测报告

日期：2026-10-20。方法与运行步骤见 [VIDEO_LINK_TEST.md](VIDEO_LINK_TEST.md)。

## 可以确认什么

第三轮在真实摄像头、天空端和 MK32 以太网链路上，统计 60 秒：**RTP 末包输出到 UART ACK 返回的闭环中位数 45.33 ms，P95 57.96 ms，最大 114.86 ms**。60 个视频 ACK 全部精确匹配，0 个未匹配。

本测试接收器没有解码和屏幕显示，因此该值不是玻璃到玻璃延迟。闭环还包含 UART 回程和 Nano 接收解析，通常比单纯的视频到达耗时更大。本轮未重现持续约 0.5 秒的接收积压，但不能据此保证正式播放器不会积压。

**不能给出可靠单向图传数字。** 同轮 PING RTT 中位数 83.40 ms，用邻近 RTT/2 扣减得到的粗估中位数 2.92 ms，但 60 个样本有 18 个负值。这个估计方法在当前链路上的误差已不可忽略，2.92 ms 不作为有效图传延迟结论。

## 环境和统计边界

| 项目 | 条件 |
|---|---|
| 采集/编码 | `/dev/video0` MJPEG 1280×720、30 FPS；x264 veryfast、zerolatency、6000 kbit/s、GOP 30、B 帧 0 |
| 视频路径 | Nano `192.168.144.129:8554/live` → MK32 `eth0` `192.168.144.20`；RTP/UDP |
| 确认路径 | MK32 `/dev/ttyHS0` → 数传 → Nano `/dev/ttyTHS0`，115200、8N1 |
| Android 程序 | test 目录独立 dex，`app_process`；正式 App 暂停，无解码/渲染负载 |
| 调试 | Wi‑Fi ADB，采样期间不流式拉取日志；视频 socket 绑定 eth0 |
| 采样 | 每秒选一帧 ACK，预热 10 秒，统计 60 秒 |

正式测厚/数传进程在采样时暂停，由测试程序独占 UART。本轮不代表测厚业务满负荷下的图传表现。RTP 起点是软件 pad，不是物理网卡出线时刻；终点是测试接收器按序收齐一帧，不是 Media3 或显示屏。

## 有效校准轮结果

Nano：`results/video_ack_20261020_194924/`。
Android：虚拟机 `test/camera_delay_test/results/android_20261020_194931/`。

| 指标（60 个样本） | 中位数 ms | P95 ms | 最大 ms |
|---|---:|---:|---:|
| RTP 末包输出 → Nano 收到 ACK | 45.33 | 57.96 | 114.86 |
| RTP 首包输出 → Nano 收到 ACK | 46.15 | 58.90 | 115.64 |
| H.264 输出 → Nano 收到 ACK | 46.38 | 59.10 | 115.86 |
| 同进程、同负载 PING RTT | 83.40 | 96.21 | 105.46 |
| Android 收帧 → 准备 ACK | 0.044 | 0.071 | 0.072 |

Android 全程约 75 秒收到 51,833 个 RTP 包，判定 2,233 帧完整、9 帧损坏/不连续，发出 74 个视频 ACK；预热和窗口外 ACK 不计入上表。UART 解出 71 个 PING，CRC 错误 0；统计窗口内收到 60 个有效校准响应。损坏帧计数可能受缺包或乱序影响，不等于精确丢包率。

首轮约 1 秒异常样本保留，不能由目前日志确定发生在图传方向还是 ACK 回程，不删除、不混入第三轮统计。第二轮每秒选帧与 60 秒窗口边界产生 59 个样本，不用复制样本补足。

前两轮串口读到了字节，但最高位被清除：MAVLink `FD` 变为 `7D`，导致 PING 解码失败。短时诊断确认测试程序的串口配置存在 `istrip/parmrk` 问题；保存格式重设并读回确认后，第三轮收到正常 `FD`、有效 PING 和零 CRC 错误。未将这个临时测试问题归因于正式 App 或无线断线。

## 对当前半秒显示延迟的判断

本轮大部分视频帧的“接收到达 + 数传返回”闭环低于 60 ms，说明当前受控接收路径通常没有持续半秒积压。与实物计时器约 0.1–0.4 秒的显示差值不矛盾：曝光、摄像头内部/驱动缓存、Nano 编码前处理、正式播放器缓存、硬件解码和屏幕刷新不全在本轮范围内。

下一步应在**独立测试版播放器**中区分接收、送入解码器、解码输出和实际渲染事件，或继续用同帧计时器照片/高帧率录像测显示端到端延迟。不能仅靠这次 ACK 结果把正式 App 的全部延迟归为某一个环节，也不能把等待下一 IDR 的接入时间当作稳定播放延迟。
