# 2026-10-19 开发文档

## 持续测厚开关与 MK32 串口上传

### 目标与批准范围

用户批准实现持续开关模式：下位机未来上报机构到位时开启，取消测厚时关闭；开启期间持续发布有效新数据，不能在第一条发布后清零。本轮下位机订阅仅留注释入口，不实现机构控制、XRCE-DDS、滤波或存储。串口上传适配现有安卓仓库。

### 修改内容与过程

1. manager 新增 `_is_measurement_enabled` 与 `on_measurement_enabled(bool)`，默认 false；`on_reading()` 保留原始打印，只在开启时持续发布有限且时间不早于开启时刻的数据。
2. 新增 `/measurement/set_enabled`（std_srvs/SetBool）作为终端调试入口。未来下位机回调复用同一入口，当前没有创建下位机订阅器。
3. robot_interfaces 新增 MeasurementControl、MeasurementResult。会话 ID 区分 manager 重启，generation 区分不同开关周期；原始读数嵌套保留在结果中。
4. 新增 telemetry_bridge 包。ROS 节点只适配订阅、会话筛选和单位策略；TelemetryLink 管理串口和队列；RemoteProtocol 实现本次使用的 MAVLink common 子集。
5. 数传接收当前启用周期的结果，编码 NAMED_VALUE_FLOAT / THICKNESS；心跳 1 Hz、PING 应答、MEAS_RUN 状态和未支持命令的 ACK=3。未伪造 STM32 在线状态。
6. 取消时停止新结果并清除未发送测厚数据；已开始写入的帧完成余下字节，避免破坏帧边界。实际发送顺序分配 MAVLink sequence，控制状态按名称合并，避免重放过期 MEAS_RUN。
7. 当前为连续实时显示流，待发测厚容量 64，满时丢最旧未发送帧并计数，过期 1 秒丢弃。断开不积压历史值；完整记录和可靠补传未实现。
8. manager 每 500 ms 刷新控制状态，数传超过 2 秒未收到刷新则关闭厚度输出。发布结果不代表安卓已确认接收。
9. XML 和原 `.sh` 加入可选数传启动参数，保留原采集启动方式。同步 CMake/package 依赖。
10. README 代码树、系统架构、节点通信图、接口参考、数传模块和联调指南同步。AGENTS 区分 Orin↔STM32 的 XRCE-DDS 与 Orin↔MK32 的 MAVLink。

### 安卓协议依据与限制

只读核对 `dual_magnetic_android_software` 提交 `30d58f65b23b016cad24a29efe6a82ddd96b7263`，没有修改该仓库。地址为 Orin 1/191、安卓 255/190，数据名称 THICKNESS。

安卓固定显示 µm，采集当前单位 unknown。默认拒绝把未知单位值发送为 µm；显式 `telemetry_allow_unknown_unit:=true` 仅用于原始值联调，不能当作单位确认。安卓 decoder 收到厚度/MEAS_RUN 时会更新 STM32 在线图标，当前这个图标不能作为真实下位机在线证据，尚待安卓后续修正。

### 端口确认与环境

载板 V2.X 手册第 4 页（PDF 第 6 页）注明串口 1：RX 模组 205、TX 模组 203、3.3 V 电平。结合 NVIDIA Orin UART1 对应 serial@3100000 的说明，与系统实际设备树/tty 对照，当前端口为 `/dev/ttyTHS0`。内核控制台使用 ttyTCU0/ttyAMA0；nvgetty 和相应 serial-getty 未运行，未发现该端口被其他用户程序占用。

Compose 新增 `/dev/ttyTHS0` 映射并重建开发容器。容器内设备存在，robot 用户属于 dialout 组；宿主机源码和构建目录保留。默认数传端口改为 ttyTHS0，115200、8N1。

使用 `.sh + XML` 启动三个节点，采集路径使用不存在的测试设备，数传使用真实 ttyTHS0。实际日志显示 `port_open=true enabled=false written=0 errors=0`；SIGINT 后三个进程正常退出。没有读取真实测厚仪或发送模拟厚度。

### 真实串口探测结果

新增 `tools/probe_telemetry.py`。探测只发送 Orin 心跳并应答 PING，不发机构动作或测厚控制命令。

- 首次 15 秒：接收 1132 字节，解析 21 条 REQUEST_DATA_STREAM；其余字节没有被解析为有效 MAVLink。
- 后续 8 秒带原始捕获：接收 700 字节，14 条 REQUEST_DATA_STREAM，448 个零字节被独立解码器报告为 Bad prefix。不能将这些零字节直接认定为硬件故障。
- 有效请求源地址 255/190，目标 1/1，MAVLink 2；未观察到仓库代码预期的 HEARTBEAT/PING。
- 因此已确认真实 UART 有有效 MAVLink 输入，尚未确认安卓自研程序与 Orin 双向握手、下行接收及厚度显示。
- 证据：`real_uart_probe.log`、`real_uart_details.log`、`real_uart_rx.bin`、`launch_real_uart.log`，均在忽略的 log 目录。

### 遥控器资料核对与后续定位

## 摄像头读取、共享图像和 H.264/RTSP 实现

### 目标与完成条件

用户批准一个采集节点向视频上传和后续视觉节点共享图像的框架，并要求生成代码和测试。本轮实现采集、视频两个可组合节点；视觉处理包仍为规划。完成条件为可构建、真实 USB 摄像头采集、H.264 编码和本机 RTSP 解码、第二图像订阅者正常，以及启停和异常路径可验证。

### 修改内容

- 新增 camera_driver：CameraTypes、CameraDevice、CameraCaptureNode；采集在独立工作线程执行，发布 bgr8、未标定 CameraInfo 和诊断状态。
- 新增 video_streamer_transmission：VideoTypes、VideoPipeline、VideoStream、VideoStreamerNode；ROS 回调只交付只读图像引用，工作线程负责 appsrc、x264enc、RTP 和共享 RTSP 服务。
- 两节点通过 XML 加载到同一 component_container_mt，开启进程内通信；图像 QoS BestEffort/Volatile/KeepLast1。内核到 GStreamer、ROS 像素及编码输入仍存在复制，不宣称整条链路零复制。
- 新增 inspect_camera.sh、start_video.sh、test_video_pipeline.py。启动脚本区分宿主/容器，提供运行锁和本次进程退出清理。
- Dockerfile 加入 GStreamer 开发、编码/解码、RTSP、v4l-utils 及 Python GI 测试依赖，当前容器已安装。不重建正在使用的容器。
- 状态复用 diagnostic_msgs，图像复用 sensor_msgs，未新增自定义视频 ROS 消息。同步 README 树、目录、系统架构、通信图、接口、模块和联调文档。

### 实施与问题定位

设备树型号为 NVIDIA Orin Nano Developer Kit，宿主 R35.6.1，容器 ROS 2 Jazzy。Orin Nano 无 NVENC，因此采用 x264enc 软件编码。v4l2-ctl 确认摄像头有 MJPEG/YUYV，没有列出 H.264。MJPEG 1280×720 支持 30/60 FPS；YUYV 同尺寸仅 10 FPS。默认实际模式 MJPEG 1280×720@30，编码目标 2000 kbps。

首次 XML 启动暴露 Jazzy 的 ComposableNodeContainer 需要 namespace，补充 namespace=/ 后组件正常加载。首版测试用固定端口探测遇到关闭连接后的端口占用检查误判，改用操作系统分配的动态测试端口。测试退出仅通知 launch，由 launch 通知组件，避免向整个组重复发 SIGINT。上述均已修复并重跑。

服务停止会关闭监听、会话和客户端，相机仍采集。端口冲突返回失败，释放端口后可重新启用。图像停止时不重发最后一帧；超时进入 WAITING_FRAME。解码样例画面模糊，未将链路通过表述为光学清晰度通过。

### 卡顿后持续约 1 秒延迟的定位结论

遥控器重新连接后，视频节点持续处于 STREAMING，8 秒内接收帧和编码帧均增加约 240 帧，约为 30 FPS；`dropped_frames` 未增加，节点无错误。Orin 到遥控器 RTT 约 9～14 ms，整机仍有约 38% CPU 空闲，因此没有证据表明当前 1 秒持续延迟由 Orin 停止采集、发送端帧队列继续增长、网络基础时延或 CPU 饱和造成。

当前客户端协商为 RTP/UDP。GOP 30 会使新客户端或解码器丢失参考帧后最多等待约 1 秒到下一关键帧，但它本身不能完整解释恢复后长期固定落后约 1 秒；长期落后更符合安卓播放器在 BUFFERING 后继续消费旧的 RTP/解码/渲染队列、未重新追到直播边缘。最优修复分为两端：Orin 将 GOP 调为 10、VBV 调为 100 ms、appsrc 与编码前队列各缩为 1 帧，以缩短接入和损坏恢复；安卓在 BUFFERING 超过约 500～700 ms 时完整停止并释放旧 ExoPlayer，清空 Surface 和 MediaItem，再创建新 RTSP 会话，确保丢弃旧帧。RTP/TCP 作为丢包对照项，可减少 damaged access unit，但弱网重传可能形成新的延迟，因此不把强制 TCP 当作唯一修复。
