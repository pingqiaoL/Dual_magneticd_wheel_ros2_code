# 摄像头与视频模块

更新：2026-10-23。已将低延迟测试中的生产逻辑迁入正式 src，计时探针仍在 test/camera_delay_optimize。

## 数据流

```text
/dev/video0 → CameraDevice：MJPEG 解码 → 紧凑 I420
  → CameraCaptureNode → /camera/image_yuv (yuv420)
                         ├─ VideoStreamerNode → 最新帧 → x264 → RTSP/RTP
                         └─ BgrConverterNode → /camera/image_raw (bgr8) → OpenCV/算法
```

三个组件通过 video.launch.xml 在同一多线程容器加载并启用进程内通信。只有采集组件打开设备。BGR 组件没有下游订阅时跳过颜色转换，转换工作不在采集线程中运行。队列深度为1，慢消费者允许丢弃旧图像。

## 图像契约

| 话题 | 布局 | 使用方 |
|---|---|---|
| /camera/image_yuv | sensor_msgs/Image，encoding=yuv420，width=W、height=H、step=W，数据 W×H×3/2 字节，Y/U/V 连续排列 | 编码器、需要原生 I420 的算法 |
| /camera/image_raw | sensor_msgs/Image，bgr8，step=W×3 | 原 OpenCV 查看器与视觉算法 |
| /camera/camera_info | 未标定，K[0]=0 | 标定消费者 |
| /camera/status、/video/status | DiagnosticArray | 运行状态和计数 |

header.stamp 为应用获取完整帧的时间，不是曝光时间。I420 是本工程明确的平面布局契约，消费者需按上述布局处理，不能假定 cv_bridge 自动支持该编码。

## 默认与调参

默认1920×1080 MJPEG采集60 FPS，编码输出30 FPS、6000 kbit/s、GOP 10、baseline、无B帧、zerolatency、ultrafast、threads=2、sliced-threads=true。摄像头必须支持对应模式；否则使用支持的采集帧率。

相机 appsink、编码 appsrc 和编码前队列均限制旧帧积压。max_frame_age_ms=150 仅限制应用帧年龄，并不保证端到端150 ms。SPS/PPS 随关键帧发送。没有客户端时不进行H.264编码，但采集仍运行。

默认值由 launch 和配置提供，普通 C++ 配置同步保持一致。编码和采集帧率独立；编码线程按输出频率从最新帧槽取图，不循环发送旧图。

## 操作

```bash
# 宿主机进入容器
docker exec -it robot_ros2_dev bash
# 容器内默认视频
bash /workspace/activate/single_module/camera.sh
# 设备仅支持1080p30时
bash /workspace/activate/single_module/camera.sh video_capture_frame_rate:=30
# 停止整条视频链（相机+编码）
bash /workspace/activate/internal/stop_video.sh
```

完整参数见 activate/README.md，本地原图查看见 docs/module_test.md。

## 测试与结果边界

test_camera_device 检查 I420 布局、停止/重启和设备缺失重连。tools/test_video_pipeline.py 验证双路图像消费者、RTSP解码、多客户端、服务重启、旧帧拒收及退出释放端口。

历史A/B：60采集/30编码+2切片线程的 V4L2输出到H.264中位约38 ms、P95约47.7 ms；这些是软件分段耗时。最近用户反馈端到端约260 ms，本次迁移后绝对延迟和运动画质待另行实机复测，不声明已达到200 ms。
