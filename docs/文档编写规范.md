# 软件项目文档编写规范

文档状态：现行  
适用范围：本仓库 README、架构、模块、接口、测试及开发记录  
更新日期：2026-10-16

## 1. 基本原则

1. 一篇文档只服务一个主要目的：学习、操作、查阅或理解。
2. 当前实现、候选设计、实测事实和后续规划必须明确区分。
3. 代码变更涉及接口、结构或运行行为时，同一提交更新相关文档。
4. 同一事实指定一个主要维护位置，其他文档使用链接，避免复制后失去同步。
5. 命令必须标明在 Windows、Orin 宿主机还是 ROS 容器中执行。
6. 操作步骤同时写出预期结果和失败后的检查入口。
7. 图中的方框表示组件，箭头必须标注调用、消息或物理连接含义。
8. 文档说明行为和理由；源代码注释主要解释局部约束及代码无法表达的原因。

## 2. 文档头信息

现行设计和参考文档开头包含：

```text
文档状态：草案 / 待审批 / 现行 / 已废弃
实现状态：规划 / 部分实现 / 已实现 / 已实机验证
适用版本：Git 提交或“工作区未提交”
更新日期：YYYY-MM-DD
```

历史开发记录使用日期作为标题，不修改过去的测试结论；若结论失效，在现行文档中写明替代关系。

## 3. 模块设计文档模板

```markdown
# 模块名称

## 目的与范围
解决的问题、输入输出和职责边界。

## 环境与约束
硬件、系统、线程、资源、时序和权限限制。

## 结构与职责
模块图、各类职责、依赖方向和源码位置。

## 运行过程
启动、正常流程、异常恢复和停止流程。

## 接口与数据
公开函数、ROS 接口、数据结构和调用约定。

## 异常处理
错误检测、上报、重试及状态清理规则。

## 设计依据
候选方案、当前选择、理由及代价。

## 验证
验收条件、测试入口、实际结果和证据。

## 已知限制
尚未支持或尚未实机验证的内容。
```

## 4. 接口参考要求

函数接口说明至少包含用途、参数、单位、返回值、资源所有权、并发约束、错误行为和超时语义。ROS 参数说明类型、默认值、范围、何时生效及非法值行为；话题说明发布者、订阅者、消息、QoS、频率和时间戳语义；字节协议说明偏移、长度、字节序、校验范围和经验证报文。

## 5. 每日开发记录模板

```markdown
## 任务名称

### 目标与完成条件
为什么修改，什么结果算完成。

### 修改内容
文件、接口和行为变化，关联现行设计或 ADR。

### 实施与问题定位
保留关键发现和依据，不粘贴无关终端输出。

### 验证
环境、命令、预期、实际、证据和结论。

### 遗留项
尚未完成或尚未验证的内容。
```

## 6. 审核清单

- 标题和文件名能否让读者找到内容。
- 是否明确适用版本与实现状态。
- 结构图、运行图和代码实际职责是否一致。
- 接口是否包含单位、边界、超时和错误语义。
- “通过”是否有对应的测试范围和证据。
- 是否混入已删除接口或尚未实现能力。
- 文档内链接、命令和文件路径是否仍然有效。

## 7. 参考方法

- [Diátaxis](https://diataxis.fr/)：教程、操作指南、参考和解释四类文档。
- [arc42](https://arc42.org/overview/)：系统边界、构建块、运行、部署、决策、质量和风险。
- [Google Documentation Best Practices](https://google.github.io/styleguide/docguide/best_practices.html)：文档随代码更新，保持精简并减少重复。
- [MADR](https://adr.github.io/madr/)：用简洁模板记录重要设计选择及理由。
