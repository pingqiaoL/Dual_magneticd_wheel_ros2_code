# 2026-10-22 开发文档

## 今日目标

重构 MK32 数传模块的职责边界：ROS 应用层只决定发送哪些业务数据，底层驱动自行处理串口读写、心跳、应答和重连，移除由 ROS 10 ms 定时器推进通信的设计。同时保留实时数据“只发新值、断线不积压旧值”的现有行为。

## 完成内容

### 数传驱动

- 以 `TelemetryDriver` 替换 `TelemetryLink`。公开接口收敛为 `start()`、`stop()`、`send_named_float()`、`send_named_int()` 和 `status()`。
- 驱动创建单一工作线程，串口的打开、读取、写入和关闭全部在该线程内完成。
- 使用 Linux `poll()` 同时等待串口描述符和内部 `eventfd`：
  - 串口可读时解析 MAVLink 报文；
  - 有待发帧时才等待串口可写；
  - 新业务数据和停止请求通过 `eventfd` 立即唤醒；
  - 心跳、重连和遥测过期时间共同决定最长等待时间。
- 保留 1 Hz MAVLink HEARTBEAT、PING 回复、未支持命令 ACK、部分写续传、有界队列、过期丢弃和自动重连。
- 驱动断线期间拒绝新的实时遥测，重连后等待新数据，避免旧测厚结果在链路恢复后补发。

### 应用层与公共串口接口

- `TelemetryBridgeNode` 删除 10 ms I/O 定时器和 `process_device_io()`；构造时启动驱动，析构时停止驱动。
- 测厚回调仅校验消息并提交 `THICKNESS`；应用层以 1 Hz 定时器提交临时的 `STM_LINK=0`。真实下位机接入后由应用状态替换该固定值。
- `SerialPort` 增加只借用、不转移所有权的 `native_handle()`，供拥有串口的驱动线程执行就绪等待。外部不得关闭或重新配置该描述符。
- MAVLink named value 名称限制为 1～10 个可打印 ASCII 字符，拒绝换行等控制字符。

### 代码与文档

- 更新数传模块、系统架构、节点流程和代码目录文档，统一使用 `TelemetryDriver` 名称及新的调用责任。
- 原 `TelemetryLink` 源码、测试和旧生成产物已保存到可恢复证据目录，没有直接覆盖删除。

## 最终结构

```text
TelemetryBridgeNode
  ├── 订阅 /measurement/thickness
  ├── 校验业务消息
  ├── send_named_float("THICKNESS", value)
  └── send_named_int("STM_LINK", state)
                    │
                    ▼
TelemetryDriver（单一工作线程）
  ├── eventfd：应用提交与停止唤醒
  ├── poll：串口读/写事件等待
  ├── 实时遥测队列与协议控制队列
  ├── 心跳、超时、断线和重连
  └── RemoteProtocol + SerialPort
```

`process_io()` 这一职责仍存在于驱动内部事件循环中，但不再成为应用层 API。这样节点无需知道串口检查周期，也不会把设备调度逻辑混入 ROS 回调。

## 数传与图传延迟复测

完成正式 App 数传 RTT、视频负载下数传 RTT、Nano 采集与编码分段、真实 RTP 到达闭环以及正式 App 稳态播放诊断。详细方法、指标和边界见 `test/camera_delay/RETEST_2026-10-22.md`，机器摘要见同目录 `RETEST_2026-10-22.json`。

- 正式 App 60 次 PING 全部返回：RTT 中位数 73.86 ms，P95 85.57 ms。
- 视频负载下独立探针 60 次 PING 全部返回：RTT 中位数 75.71 ms，P95 87.61 ms。
- Nano V4L2 源到 H.264 输出：中位数 44.16 ms，P95 49.18 ms，约 29.9 FPS。
- RTP 末包输出到遥控器收齐并经数传返回 ACK：中位数 45.92 ms，P95 63.98 ms；该值包含数传回程。
- 正式 App 稳态播放缓冲中位数 156 ms、P95 185 ms，渲染 29.90 FPS，解码丢帧 0；采样期间未出现持续积压。
- 正式联合入口与 App 播放均已恢复。本轮测试未修改正式源码或 APK。

## 1080p 采集与码率优化测试

新增隔离测试目录 `test/camera_delay_optimize/`，测试代码通过复制当前摄像头和视频包到 `/workspace/log/camera_delay_optimize_*` 后加入计时点，不修改正式业务源码。测试使用 `/dev/video0` 的 MJPEG 1920×1080@30 FPS，分别比较 H.264 6000 与 8000 kbit/s；每组预热 5 秒、统计 30 秒。

| 配置 | 采集 FPS | 编码输出 FPS | V4L2→H.264 中位数 / P95 | 编码与解析中位数 / P95 | CPU 中位数 / P95 |
|---|---:|---:|---:|---:|---:|
| 1080p、6000 kbit/s | 29.90 | 23.13 | 90.14 / 107.75 ms | 26.31 / 34.62 ms | 56.70% / 60.23% |
| 1080p、8000 kbit/s | 29.90 | 21.23 | 95.63 / 112.16 ms | 30.16 / 36.97 ms | 58.43% / 62.37% |

摄像头能够稳定完成 1080p/30 FPS 采集，但当前 Orin Nano 软件 H.264 管线只能输出约 21～23 FPS。单帧丢旧队列阻止旧帧积压，因此表现为输出帧率下降，而不是延迟无限增长。8000 kbit/s 同时增加编码耗时、CPU 和网口负载，没有改善输出帧率，暂不采用。

测试结束后已恢复原组合入口，并核对正式节点参数为 1280×720、6000 kbit/s；摄像头、视频、测厚、manager 和数传节点均已恢复。详细报告见 `test/camera_delay_optimize/REPORT.md`，原始结果见 `test/camera_delay_optimize/results/run_20261022_214154/`。
